# 0006 · 真实行情数据接入，下线确定性合成行情

- 状态：已采纳
- 日期：2026-11-07
- 关联：0001（四层分包与确定性合成行情，其中「合成行情」部分被本文取代）
- 关联：SRS K-12（复权一致性）、FR-DAT-06（涨跌停）

## 背景

第一版用 `zlib.crc32` 播种生成的日线跑通了「行情 → 选股 → 信号 → 持仓 → 风控」
全链路（见 0001）。它解决了工程验证问题，但也带来两个死结：

1. **结论不可信**。合成数据里「ROE 大于 15%」筛出的 12 只票，跟真实市场毫无关系。
   工作台的第一性用途是辅助决策，数据一假，上面所有功能都是玩具。
2. **字段无法真实**。主力净流入、股息率、量比这类字段没有「合理编造」的算法——
   要么接真源，要么这个字段的意义就不成立。

同时 0001 的一条设计被证明是对的、值得保留：**只存不复权原始价 + 复权因子**，
复权在返回时合成。它让「换个复权口径」不需要重算历史。

## 决策

### 1. 新增 `packages/data`，夹在 core 与 engine 之间

依赖方向变成 `core → data → engine → api → web`。

- `data` 只依赖 `core`，负责抓取、落库、算因子，**不认识任何业务概念**
- `engine` 不再自己造数据，全部经 `repo` 读库；取不到就返回空 + `available: False`
- `api` 只多挂一个 `/data/*` 路由，传输层不知道数据从哪来

这样换数据源时，`engine` 及以上一行不用改。

### 2. 数据源分工：按「哪个接口真的能跑完 5000+ 次请求」来定

全量同步需要约 1.1 万次 HTTP 请求。实测下来只有一种组合能跑完：

| 用途 | 选定的源 | 理由 |
| --- | --- | --- |
| 全 A 名单 / 横截面快照 | 新浪 `Market_Center` | 唯一能连续翻 56 页不断的接口 |
| 个股与指数日线 | 新浪 `CN_MarketData.getKLineData` | 并发 100 只 5 秒、100% 成功 |
| 个股日频资金流 | 新浪 `MoneyFlow.ssl_qsfx_zjlrqs` | 给主力净额与超大单净额 |
| ROE + 行业分类 | 东财 `datacenter` `RPT_LICO_FN_CPD` | 一次请求覆盖全市场，含东财二级行业 |
| 分红送配（复权源 + 股息率） | 东财 `datacenter` `RPT_SHAREBONUS_DET` | 唯一给得出每股派息与送转比例的公开源 |
| 指数成分股 | 东财 `datacenter` `RPT_INDEX_TS_COMPONENT` | 官方成分表，按 TYPE 区分指数 |
| 指数实时点位 | 腾讯 `qt.gtimg.cn/q=` | 批量 60 只 0.44s，只用于实时报价 |

**东财 `push2` 系列（横截面与 K 线）已弃用**：连续请求 8 次全部
`RemoteDisconnected`，拉黑后不可控时间内不恢复。它的 `datacenter` 是另一套网关，
稳定可用，但只提供财报与成分表这类横截面，不能替代行情。

**腾讯 `ifzq` / `proxy.finance` 已退出日线**：两个域名**交替**返回 HTTP 501
（反爬网关拒绝，不是限速，等多久都一样）。一次全量同步 3973 只只入 502 只，
大量空结果被静默跳过，是最危险的一种失败——不报错，只是数据变少。

### 3. 复权因子用分红送配**精确推算**，不用比例近似

新浪只给不复权价。复权因子按下式逐事件推算：

```
除权参考价 = (除权前收盘 − 每股派息) / (1 + 送转比例)
该日之前的全部价格 × (参考价 / 除权前收盘)
```

多事件连乘，从最后一根 K 线往前累乘，`adj[i]` 表示「第 i 根相对最新一根的前复权系数」。
`qfq = raw × adj`，`hfq = raw × adj / adj[-1]`。

这比「按涨跌幅反推」准，因为它只需要分红方案公告的数字，不依赖任何价格假设。

**锚点是窗口内最后一根**。所以：

- 全量 520 根与增量 12 根都以最新交易日为锚，两者算出的 `adj` 在重叠区间一致
- 一旦增量窗口内出现除权事件，必须**整段重建**（`_needs_rebuild`）：
  除权会改写全部历史因子，只补最近 12 根会在时间轴上留下断层

### 4. 因子宽表：同步时一次算完，读路径不碰日线

`factor` 表按 `(trade_date, code)` 存 34 列。选股、排序、市场温度全读这张表。

不这么做的话，5000+ 只票的 34 个因子要在每次请求时现算——单次 20~40 秒，
任何交互都不可用。代价是同步变慢一点，换来读路径 O(1)。

### 5. 存储：SQLite + WAL，增量可续跑

`data/alphaforge.db`，11 张表，`journal_mode=WAL`、`synchronous=NORMAL`、
`mmap_size=256MB`。单文件、零运维、可直接复制备份。

增量逻辑：库里已有的票只补最近 12 根，没有的整段拉 520 根
（只给 12 根画不出图，也进不了因子表）。

### 6. 断网回放

所有读路径只查库，不触网。唯一的例外是个股分时（`minute`）：
实时抓、写 `minute_cache`、带 `stale` 标记，抓不到就返回缓存并标记为旧数据。
因此断网时工作台整体可用，只有分时图会显示为缓存。

## 实测踩到的坑（都已写进代码注释）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 新浪代码格式 | `600519.SH` 写成 `600519sh` 时 HTTP 200 + 返回 `null`，不报错 | 统一 `_sym()` 转 `sh600519` 前缀式 |
| 新浪翻页上限 | `num` 最大 100，给 1000 也只回 100 | 56 页翻完按 code 去重 |
| 东财 datacenter 上限 | `pageSize` 最大 500，给 1000 回 500 | 分页 + `max_pages` 安全阀 |
| 东财 `_dc` 无上限 | 配 50 万页的报表永远不退出，任务挂死 | 所有调用强制传 `max_pages` |
| 腾讯日线行序 | 是 `[日期, 开, 收, 高, 低, 量]`，**不是 OHLC** | 逐字段赋值，不按位置解包 |
| 反爬拒绝 ≠ 限速 | 403/429/501 重试只会把整个域名耗死 | 单独 `BlockedError`，立刻换域名 |
| 停牌票 `trade=0` | 市值、流通股本全算成 0 | 用 `settlement`（昨收）兜底算 |
| 指数无成交额 | 新浪指数 K 线只给成交量 | **写 0，不拿「量 × 点数」编造** |
| **ROE 是累计值** | `WEIGHTAVG_ROE` 是年初至今口径，三季报的 ROE 不是年化 ROE | **只取年报**（`latest_annual_date`）。否则一季度就得「三个月赚 15%」，全市场几乎没有银行能过 15% |
| **量比源不提供** | 新浪快照没有量比字段，`snapshot.volratio` 恒为 NULL | 由日线自算「当日量 / 5 日均量」写进因子表，`quotes()` 优先读因子表 |
| **成交额三种单位并存** | `daily.amount` 元、`factor.amount` 亿、`index_quote.amount` 亿 | 定死：跨 API 一律「元」，指数价格类一律「亿」，各层注释写清 |
| **涨停强度斜率** | 早先 `×8`，净涨停 7 家以上就顶到 100 分，这一项等于常满分 | 改 `×0.8`，常态净涨停 -30~+80 家落在 26~100 分之间 |
| **增量误判成重建** | 除权重判用了整批的 `incremental` 标志，全量拉的 520 根撞上两年前分红就被判成「需重建」，既不落盘也不计失败 | 逐只判断是否走的增量（`fetch_one` 返回 `inc`） |
| **领跌榜取错** | 成分表按涨幅倒序截断 200 条，尾部是「涨得最少的」而不是「跌得最多的」 | 单独按 `change_pct ASC` 取一份 `laggards` |
| **别名带空格不匹配** | 词典写「站上20日线」，用户写「站上 20 日线」 | 查询串与别名词典都用 `normalize_text` 去空白 |
| **时序算子被别名吃掉** | 「连涨 3 天」里「连涨」先命中别名，剩「3 天」没有比较符，条件静默丢失 | `_UP_DAYS_RE` 抢在别名之前抽 `up_days >= N` |
| **同句行业丢失** | 「ROE 大于 20% 的白酒」先抽指标就 `continue`，行业没被处理 | 行业/板块抽取提到指标之前（它不消费文本，先跑无副作用） |
| **单行业被分散规则砍** | 说了「取 3 只白酒」，每行业最多 2 只的规则只给 2 只 | 条件里已把行业/板块限死时，放开 `max_per_industry` |
| **`code` vs `codes`** | 报价接口只认 `codes`，写成 `code` 不报错、静默返回全池 5568 条 | 两个参数名都接受 |
| **「字段必填」是演示期的幻觉** | `repo.search` 只回 4 列（code/name/industry/board），前端类型却声明 `price: number` 并直接 `.toFixed()`。键入第一个字符拿到结果就抛 `TypeError: Cannot read properties of undefined (reading 'toLocaleString')`，整个 `el-dialog` 渲染失败 → **弹窗自己关了** | 后端 `search` 补 `LEFT JOIN factor` 带出 price/change_pct；前端格式化函数统一对 `null/undefined` 退化为「—」，类型标注改 `number \| null` |

倒数第二条是这一轮最贵的一课：演示池 40 只票字段永远齐全，
`price: number` 这条类型声明从来没有被真实数据证伪过。换成 5578 只之后，
**次新股 / 退市股在因子表里根本没有行**，于是「渲染期拿 undefined」从理论风险
变成了必现故障——而且它伪装成 UI 问题（弹窗关闭），实际是数据契约问题。
教训：真实数据下任何跨层字段都要先问一句「这行一定存在吗」，
空值必须走「显式显示「—」」这条路，而不是让它去撞 `.toFixed()`。

最后一条是刻意的：宁可界面上少一个数字，也不要出现一个看起来合理、实则错误的数字。

## 备选方案与被否理由

| 方案 | 否决理由 |
| --- | --- |
| 继续用腾讯做日线 | 两域名交替 501，1.1 万次请求跑不完，且失败是静默的 |
| 用 akshare / tushare 等第三方库 | 引入依赖、封装了同样的接口但没有更稳，出问题要穿透两层排查 |
| 用东财 `push2` 做全市场横截面 | 拉黑后不可控时间不恢复，一次失败全量同步就废 |
| 复权用「后复权比例近似」 | 分红送转的现金流细节丢失，长期历史误差累积到十个点以上 |
| 因子查询时现算，不建宽表 | 单次 20~40 秒，交互完全不可用 |
| 存前复权价而不是原始价 + 因子 | 换口径要重算全表；且原始价是不可再生的原始事实 |

## 后果

**得到**

- 5578 只全 A、520 根日线（合计 282 万行）、34 列因子全部真实；行业分类用东财二级（如「白酒Ⅱ」「光伏设备」）
- 4122 只票有真实复权因子（分红送配推算生效），零价行为 0
- 选股、AI 问股、市场温度、指数成分结构的数字都可以对外解释来源
- 断网可用，只有分时图会标记为缓存
- `packages/data` 可独立 `python -m alphaforge_data sync --only daily` 跑，不依赖 Web 进程

**实测同步耗时（全量，workers=12）**

| 步骤 | 行数 | 耗时 |
| --- | --- | --- |
| universe | 5578 | 15.6s |
| fundamentals | 5577 | 2.5s |
| bonus | 3737 | 4.2s |
| daily | 2,283,690 | 565.2s |
| flow | 167,170 | 560.4s |
| index | 3640 | 2.0s |
| factor | 5568 | 32.3s |
| **合计** | | **约 19 分钟**，全程零失败 |

**代价与已知限制**

- 全量同步约 15 分钟（6 只/秒，受新浪同主机 0.1s 间隔约束），之后增量只补 12 根
- 新浪日线不返回成交额。历史成交额用「量 × (开+高+低+收)/4」估算，
  **最新交易日会用快照的真实成交额覆盖**（`step_daily` 末尾的 UPDATE）。
  也就是说：当日准确，历史为估算值
- 指数日线无成交额，`index_daily.amount` 恒为 0（下游不展示，不编造）
- 资金流只有主力/超大单净额，大单由净额减超大单反推，中单/小单**留 0 不编**
- 停牌股若在停牌期间除权，`adj` 锚点会落在它自己的最后一根而非全局最新日，
  产生极小概率的因子错位。当前不处理，因为停牌期间除权本身极罕见
- 0005 中「`options` 由演示池反推（行业 19 个）」已失效：行业下拉改为运行期从
  `symbol.industry` 取真实分类，`INDUSTRY_ALIAS` 改为「口语 → 关键词」映射
  （因为真实行业名是「白酒Ⅱ」而不是「白酒」）
